# Окружения Python

## Виртуальные окружения

### Создание и активация

`python -m venv .venv` создаёт изолированное окружение с собственной
копией интерпретатора и site-packages. Активация подменяет PATH:
`source .venv/bin/activate` на POSIX, `.venv\Scripts\Activate.ps1` в
PowerShell. Неактивированное окружение — просто каталог, зависимости
ставятся через `pip install -e .venv/Lib` не нужно — pip умеет
принимать `--python .venv/bin/python`.

### Зачем не системный Python

Системный интерпретатор принадлежит пакетному менеджеру ОС: обновление
ОС может заменить библиотеки под приложением. Любой проект — своё
окружение, даже одноразовый скрипт.

## Управление зависимостями

### Пиннинг версий

`requirements.txt` с точными версиями (`==`) — воспроизводимая сборка;
`requirements.in` с диапазонами (`>=`) — декларация совместимости.
Инструменты компиляции (pip-compile) переводят первое во второе.

### Транзитивные зависимости

Lock-файл фиксирует весь граф, включая транзитивные пакеты. Без него
два разработчика могут получить разные версии одной библиотеки в
пределах одного диапазона — и разные баги.

## Инструменты

### pyenv

pyenv управляет версиями самого интерпретатора, а не зависимостями:
`.python-version` в каталоге проекта выбирает нужную сборку Python.
Смешение pyenv и venv — норма: первое про интерпретатор, второе про
библиотеки.

### uv и pip-tools

uv — быстрый резолвер и установщик, совместимый с pyproject.toml;
pip-tools — зрелый pipeline in → txt. Выбор инструмента менее важен,
чем наличие lock-файла в репозитории.
